# Audit v3: entry-predictor (2026-07-25)

Triggered by a live production incident: the site shipped a fabricated "+125 entries yesterday" bar on Bradley Open (and "+32" on Pacific Coast Open) that drifted a day per run. This audit fixes that incident, re-verifies the standing v1/v2 ledgers against HEAD, and sweeps for the same defect class across the pipeline, front-end, security, and model methodology.

## Scope and method

- Target: this repo (origin `github.com/HaterAndrew/chess-prediction`, deployed at haterandrew.github.io/chess-prediction).
- Audit ref: fresh clone `origin/main@bcda7d6` (2026-07-24). All finding evidence cites file:line at that SHA. The nightly cron rewrites data files, so data-file evidence names the SHA.
- Phase 0 (incident + reliability fix) is the ONLY code applied by this audit; it lives in the working tree pending owner commit approval (04c_final_model.py, 04d_website_data_v2.py, pipeline_utils.py, auto_update.py, tests/test_daily_data_integrity.py, tests/fixtures/incident_2026_07_25/). Every other finding is filed with a fix sketch, NOT APPLIED.
- Method: baseline (fresh clone, byte-exact incident reproduction from committed CSVs, cron forensics via `gh`), two reconciliation agents re-deriving every v1/v2 finding status against HEAD, then six review sweeps with disjoint charters (N heuristics, O reliability, P front-end, Q+R validation/data-scans, S security, T methodology), a live Playwright render pass, two approved Ask-endpoint probes, and an independent adversarial verifier (V3) that re-opened every cited line and re-derived every quantitative claim on CRITICAL/HIGH items.
- Relationship to v1 (audit/AUDIT.md, categories A-F) and v2 (audit/AUDIT_2026-07-07.md, categories G-M + V1-N): v3 IDs continue at N. A regression of a closed item is tagged REGRESSION(id); a re-challenge of a closure premise is RECHALLENGE(id); overlap without regression is RELATED(id). Disambiguation: a bare `N#` is a v3 finding; `V1-N#` (always prefixed) is v2's verifier series.

## Top findings

1. **N1 (incident, FIXED)**: A missing scrape day (the 07-22 04e timeout) exposed a stale archive point that `reanchor_daily_to_event_start` had misplaced by substituting a family-median offset for a legitimately negative one; the A4 3x-jump backstop then multiplied the whole earlier curve ~3-4.6x and the monotone cleaner dropped the true tail, so Bradley Open shipped daily_data ending at 625 vs a real 197. Reproduced byte-for-byte; fixed at all three seams in Phase 0.
2. **N2 + O1 + Q1 (three live CRITICALs)**: (N2) the 04d plausibility clamp can display a final estimate *below* the current entry count — verifier confirmed it fires whenever `point > hist_max*3` and `current_count > hist_max*1.5`, with no `max(point, current_count)` floor before write. (O1) when the pipeline crashes mid-run — as it did today — every downstream step including the stale-flag stamp is skipped, so the site serves stale data with no banner (07-24 data is live right now through the 07-25 failure). (Q1) `data_health.py` has no daily_data max-vs-count/gap/monotone check and is called without `--strict`, so nothing gates: a max-exceeds-count rule would have caught this incident at commit time.
3. **T1/R2 (the public grade is wrong-low)**: the headline "D" should be "C". Two 2026 events (Chicago Class, Pittsburgh Open) are graded against curves frozen at ~0.30x of their reconcile-bumped finals (the stale-export path, J12), producing recorded T-3 errors of ~40%. Verifier reproduced the exclusion to the decimal: removing just these two moves the T-3 bucket D→C, changing the published headline.
4. **P1 (front-end has no contiguity defense)**: ~14 daily_data consumption sites derive dates/deltas from array positions assuming contiguous daily data; the Playwright render pass reproduced the incident's exact +125/+32 bars live. Even with the Phase 0 data fix, a future missing scrape day re-triggers the mislabeling — this is a client-side defense gap the data fix does not close.
5. **S2 + S1 (security)**: a PII-shaped fixture (`tests/fixtures/admin_export_sample.csv` — full names, home city/state/ZIP, minor-player→paying-parent clusters) sits in the public repo; and `/ask` is down in production (its `DATA_URL` 404s because it points at a path GitHub Pages does not serve). `/ask` fails closed (no leak), and the worker's prompt-injection blast radius is nil, SSRF is constrained, and no secret is committed.

Cross-cutting: the v1 defect class (one number, two sources, no reconciliation / a heuristic silently overriding a real observed value) is still alive — N2 (clamp overrides current count), N3 (recal overwrites CI floors), T2 (graded numbers ≠ displayed numbers), and the whole "trust the real scraped value, warn don't mutate" pattern Phase 0 applied to the incident is the recommended remediation for N2/N4/N8.
