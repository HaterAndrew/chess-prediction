# Audit v5: entry-predictor (2026-07-30)

Owner-requested health check, no triggering incident. v4 (2026-07-26) closed at `d24559d`; this pass audited the whole behavioral surface rather than a commit delta, because the presenting symptom (13 of 14 live cards frozen on interim estimates) crossed module boundaries that no delta review would have connected. Six root-caused defects were found and all six were fixed the same day. Every fix commit passed `ruff check . && pytest tests/ -q` independently; the suite grew from 331 to 380 passing (3 xfailed throughout).

## Scope and method

- Target: this repo (origin `github.com/HaterAndrew/chess-prediction`, deployed at haterandrew.github.io/chess-prediction). Pre-fix ref: `54cffd6`. Defect evidence cites file:line at that SHA; fix evidence cites the fix commit.
- Method: three read-only exploration sweeps with disjoint charters (roster/data flow, model/calibration, CI/telemetry/site), two independent planning passes to reconcile the fix ordering, then a same-day fix pass executing the approved plan. Baseline payloads (`website_data.json`, `performance_data.json`) and a production-shaped recalibration harness were captured before any code change; every model-affecting fix was verified against them.
- ID scheme: findings are namespaced `v5 <letter><n>`; code markers read `v5 Cat <letter>`. Categories: R (roster), L (calibration), T (CI truth), V (warning payload), F (fees), K (hygiene). The bare letters T and V collided with earlier series (v3 categories ended at T; V is the verifier convention), so the `v5` prefix is load-bearing: no bare-letter IDs are used anywhere.
- No formal adversarial verifier ran this pass. Verification was inline and quantitative: each Cat L change was gated on the before/after harness and the 04e fold regeneration; Cat R on the live payload diff; Cat T on an end-to-end `auto_update.py --skip-scrape` run.
